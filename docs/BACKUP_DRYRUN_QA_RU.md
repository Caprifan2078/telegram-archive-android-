# Исправление пробного восстановления — QA, 27.10.2026

## Основание
Предыдущий экспериментальный CI run 40487313684 сообщил о двух отдельных сбоях:
- при правке SHA-256 в compact `manifest.json` функция `BackupVerifier.simulate` не отклоняла архив;
- на Android API 35 (Android 15) `PRAGMA integrity_check` над FTS-индексом в режиме `OPEN_READONLY` отвергал корректную базу.

## Минимальное исправление
- В `BackupVerifier.scanBackup` данные `db/*.sqlite` проверяются по размеру и SHA-256 против `manifest.json` (включая внутренний `metadata.zip` полной резервной копии). Проверяется точный набор файлов.
- Данные для анализа сначала извлекаются в уникальный временный каталог `cache/backup-test-*`. Только этот одноразовый файл SQLite открывается `OPEN_READWRITE`; пользовательские действующие БД, исходный backup и настройки не открываются для записи.
- Вся временная область удаляется в `finally`.
- Добавлены синтетические `BackupDryRunRegressionTest`: корректная FTS база и повреждённый манифест без изменения оригинальных данных.

## Проверка
- Сборка и Android instrumented tests: [CI run 40562901077](https://github.com/Caprifan2078/telegram-archive-android-/actions/runs/40562901077), API 30 и API 35. До финального завершения run **НЕ** обозначать PASS.
- В изолированном Java smoke на исходном классе с имитациями Android/SQLite проверены: корректная копия, неверный SHA-256, отсутствующий манифест и лишняя БД; это не заменяет Android instrumentation.
- Не подтверждены: реальный смартфон владельца, 9 GB backup, signing cert, безопасное обновление старой APK.

## Безопасность
Только отдельная QA-ветка; `main` не менялась. В публичный репозиторий не передавались личные Telegram-экспорты, скриншоты, приватные видео, ключи или персональные базы. Полный приватный transfer ZIP остаётся только у владельца.
