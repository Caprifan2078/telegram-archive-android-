## Исправления текущей рабочей ветки

**Duplicate Telegram ID / reply-to**: исторически конфликт двух и более
оригинальных Telegram-ID молча сопоставлял ответ первому сообщению. Теперь
временная таблица отмечает такой ID отрицательным `message_id` и исключает
его из публикуемой карты. Все сообщения остаются в индексе, неоднозначный
ответ помечается как неразрешённый, другие ссылки сохраняются.
Схема SQLite не меняется. После исправления конфликта ID в эту же
ветку добавлен потоковый импорт HTML через jsoup `StreamParser`: HTML
читается последовательно, обработанные элементы удаляются из дерева.
Ограничение сегмента 8 МиБ; корректность и пиковая память на Android
пока не подтверждены. Добавлены Android-инструментальный и Python/SQLite host
регрессионные тесты на 3 одинаковых ID. Также добавлен синтетический Android
тест отказа второй HTML-части: старая опубликованная база и избранное
должны сохраниться без частично опубликованного импорта.

## Реально проверено

- **В текущем сеансе:** архив целиком проходит ZIP CRC; синтетический
  SQLite-сценарий «три повторяющихся ID / уникальная ссылка / отсутствующая цель»
  прошёл на хосте. Это НЕ Android-интеграционный тест.
- **В материалах предыдущих сеансов:** 0.50 QA собрана в CI,
  189 JVM-тестов PASS, 1 миллион синтетических сообщений в host SQLite.
  Эти показатели относятся к прошлой версии и **не подтверждают 0.51**.
- **Android instrumentation:** для 0.50 было 0 выполненных тестов
  (сбой запуска эмулятора); новые Android-тесты и полная сборка 0.51/0.52
  в данном сеансе не запускались. APK текущей ветки **нет**.
- **Безопасность CI:** workflows ограничены условием запуска только
  на public-репозитории; приватность репозитория не менялась,
  платные runner-минуты не тратились.

## Нерешённые приоритетные задачи

1. Полная локальная сборка и JVM/Android инструментальные тесты для
   текущей ветки на установленном Android SDK; проверить R8 и зависимости.
2. Проверить новый потоковый импорт на реальном Android, особенно
   обработку больших HTML-частей, пик ОЗУ, незавершённый HTML,
   fault-injection и атомарность публикации индексированных данных.
3. Подтвердить миграции/backup-restore на синтетических сценариях и Android.
4. Реальный QA кружков, голосовых, музыкального плеера и узких экранов.
5. Оценить точность локального поиска: словоформы, ложные совпадения,
   производительность на бюджетном телефоне.
6. Пройти code review, устранить расхождение CI workflow, затем
   рассматривать PR в `main` только после всех проверок.

## Как продолжать

Работать с `qa/v052-duplicate-id-safety-20261026`, не создавать новый проект.
Сначала `python3 qa/host_tests/test_telegram_id_collision_sqlite.py`
и `python3 qa/host_tests/test_media_fixture_independence.py`,
затем `gradle testCompactQaUnitTest assembleCompactQa` (с Android SDK),
после чего instrumentation на подходящем Android-эмуляторе/телефоне.
Перед переносом `main` сравнить обе ветки и их CI-конфигурации.
Никогда не загружать пользовательские переписки/видео/фотографии в GitHub
или Actions; тестировать только на синтетических данных.
